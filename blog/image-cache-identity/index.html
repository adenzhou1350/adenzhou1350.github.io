截图更新了，为什么评分还是旧的？

截图已经换了，模型却还在用旧结果。这次用 8 个界面状态，对照图片路径、缓存内容和请求绑定，查了问题出在哪里。

周栩丞 · Aden2026-10-03约 6 分钟

本文的实验与整理使用了 AI 编程工具辅助。这是自建界面上的受控实验，不是客户生产案例。模型、输入适配和评分流程都固定，结果只适用于这组测试。

截图更新了，评分却还是旧的

界面已经从“测试通过”变成“测试失败”，截图文件也更新了，评分结果却仍然对应旧画面。看起来像模型认错了图。我先查的是：这次评分究竟读到了哪张图？

实验用了 8 个界面状态，分成 4 对。每对先给旧状态评分，再切换到新状态，分别用四种方式做对照：

  1. 每次都对当前图片重新计算，作为参照。
  2. 始终用同一文件路径，切换时覆盖图片内容。
  3. 每张图片保存到新路径，保存后不再修改。
  4. 按图片内容寻址，同时核对请求对应的图片。

模型是固定版本的 Qwen3.5-0.8B-Base，位置编码兼容适配也相同，没有做训练。要查的是这套评分流程怎样复用图片输入。

路径没变，缓存就没有更新

如果用文件路径作为图片特征的缓存键，就可能出现这个问题。用伪代码可以写成这样：

python
features = {}

def image_features(path):
    if path not in features:
        features[path] = encode_image(read_bytes(path))
    return features[path]

save_image("screen.png", state_a)
first = image_features("screen.png")

save_image("screen.png", state_b)  # 同一路径，图片内容已经变化
second = image_features("screen.png")  # 仍命中旧内容的特征

第二次读取时，图片内容已经变了，路径却仍然命中旧缓存。可以先把两张图分别存成 screen_a.png、screen_b.png，保存后不再修改，再跑一次作对照。如果还要复用缓存，就按实际读入的图片字节计算摘要，并在记录中保留请求标识、图片摘要和返回结果，方便核对。

这段伪代码只说明旧特征是怎么被复用的，并非实验实现的逐行摘录，也不能生成下面的模型评分结果。

分类恢复了，数值检查仍有两项没过

条件8 个状态中的分类正确数
对当前图片重新计算8/8
同路径更新图片并复用缓存4/8
每次使用新的不可变路径8/8
按内容寻址并核对绑定8/8

同路径覆盖图片时，4 次切换都沿用了旧状态的分类。改成每张图使用一个新路径，分类就恢复到 8/8。这次问题可以从输入和缓存的对应关系入手处理，结果不涉及视觉模型能力的提升。

分类一致还不够，我也检查了输出数值。事先定下的通过条件是：最大 logit 差不超过 0.0625，最大选项概率差不超过 0.01，并且选择相同。和每次重新计算的结果相比，普通不可变路径、内容寻址快照都只有 6/8 通过。失败的两个状态，最大 logit 差都是 0.125；虽然最后的分类相同，仍然算检查失败。

实验一共做了 40 次评分，但只有 8 个合成状态，而且 4 对状态之间有依赖关系。不能把它当作 40 个独立真实任务，也不能用这些比例推算生产准确率。

并发请求还可能拿错图片

后续用一个确定性的 CPU 反例，复现并修正了评分入口中并发请求与图片对应错误的问题。修正后，又用前面那 8 个界面串行执行了 20 组配对步骤，结果与普通不可变路径的参照一致。

这里有两项检查：CPU 反例检查并发时的输入对应关系，模型回归检查修正后的评分结果。后者是串行跑的，20 组配对也用了已有界面，所以既不是 20 个新独立样本，也不是模型并发压测。这次测试没有覆盖所有并发规模，也没有覆盖长时间运行、真实用户操作或所有模型后端。

这次回归比较的是两种缓存方式。前一轮与重新计算相比只有 6/8 通过的数值检查，结论没有变。

先留住一个失败输入和它的预期结果，记下模型版本、提示词、图片字节摘要、请求标识与实际输出。然后固定其他条件，分别试一次关闭复用后重新计算、覆盖同一路径、使用不可变路径，看看差异从哪里出现。

分类、数值差异、并发请求与输入是否对应，需要分开检查。修完以后再跑原来的失败样例；如果给图片分配独立路径已经能解决问题，就先保留这项回归检查，等确实有需要时再增加缓存机制的复杂度。

这个案例能提供一些排查参考。它还没有验证生产提速、成本节省或跨任务泛化。
