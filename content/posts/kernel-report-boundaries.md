我在 [TIRx-harness PR #12](https://github.com/mlc-ai/TIRx-harness/pull/12) 修过一个编译日志解析问题：两个 kernel 的资源数据被拼到了一起。PR 已于 2026 年 9 月 30 日合并。下面的验证结果来自当时的记录，写这篇文章时没有重新跑 GPU 测试。

## 第一份报告没写 smem，解析器读到了下一份

`ptxas` 会在编译日志里报告寄存器、静态共享内存和 spill 等资源。如果一个 cubin 包含多个 kernel，日志里就会连续出现多份报告。原来的 `parse_ptxas` 对每个字段分别做全文搜索：寄存器读的是第一份报告，缺少的可选字段却可能从下一份补上。

PR 里的复现案例可以简化成下面这样。这是字段示意，省略了完整日志中的其他内容：

```text
报告 A / plain
  registers = 10
  未报告静态 smem
报告 B / shared
  registers = 12
  smem = 128 bytes
```

逐字段全局搜索会得到 `registers=10, smem=128`。两个数字都是从日志里读出来的，但没有哪个 kernel 用了这组资源。类型检查发现不了这个错误，单看数值也不容易察觉，拿它比较资源占用就会出错。

## 把搜索范围缩到第一份报告

API 约定返回第一份 kernel 的报告。我保留了这个约定，在提取字段之前先截取对应的文本：

- 有编译入口标记时，从第一份截取到第二份开始之前。
- 没有编译入口标记时，用函数属性报告划分范围。
- 保留对简写单份日志的兼容；当前报告没有的可选字段，解析结果中也不填。

静态共享内存字段没出现，就让它保持缺失。填入另一个 kernel 的值显然不对，填零也可能误导：没有报告静态共享内存，不等于总共享内存为零，判断动态共享内存还需要其他信息。代码和回归用例都在 [PR diff](https://github.com/mlc-ai/TIRx-harness/pull/12/files) 中。

## 用两份报告一起测，再交换顺序

只给解析器一份字段齐全的报告，测不出这个问题。回归用例把两份报告拼在一起，检查结果是否和单独解析第一份相同，然后交换顺序再检查。另一个用例专门覆盖了缺少编译入口标记的日志。

PR 中也保留了 CUDA 13.0.88、B300 环境下的真实编译复现，分别核对两种声明顺序下的第一份报告。这些针对性测试在修复前能发现错误，修复后通过；没有运行完整 NumSim / GPU 套件。

这次修改只修正了报告解析，没有改变生成的 kernel，也没有验证加速效果。以后处理编译日志、性能追踪或多任务评测时，我会先划清每条记录的范围，再提取字段和聚合指标，避免把不同对象的数据拼到一起。
